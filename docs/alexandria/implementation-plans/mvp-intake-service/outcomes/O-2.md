## Validation Criteria

- A test client can `POST` a multipart/form-data request to `/v1/feedback` carrying optional text, optional file attachments, and an optional email; the service returns a CLI-shaped confirmation body (no URL, no Report ID, no link).
- The service generates a UUIDv7 ID and writes `feedback.json` + `feedback.txt` + optional `attachments/<filename>` under `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/` in the shared S3 bucket.
- `feedback.json` includes the UUIDv7, server-captured client IP, optional email (opaque, not validated for format at this layer), Fabro version / platform / arch (passed by the client), timestamp, retention deadline, and an attachments manifest. `feedback.txt` carries the message text only.
- Within the same request, the service POSTs a Discord component-v2 payload to the `FEEDBACK_DISCORD_WEBHOOK_URL` (header / sysinfo / body / attachments tree / footer) calibrated against `bun feedback`'s `sendToDiscord` per C1; the payload tone matches the calm `bun`-calibrated register.
- There is no `GET /v1/feedback/:id`, no `DELETE /v1/feedback/:id`, no rendered page, no recall affordance — exactly one route exists for Feedback (`POST /v1/feedback`).
- The Fargate request body size limit is 25 MB (sized to Discord's webhook attachment ceiling); oversized requests are rejected in the calm tone register.
- IP is captured to `feedback.json` and CloudWatch only — never to Sentry, never to a DynamoDB cache, never hashed at rest, never used for analytics or cross-submission joins.

## Motivation

The Feedback flow is the second of the two intake types the library has committed to forever ([[Principle - Narrow Forever]]). It is structurally distinct from the Report flow in every dimension that matters (ID shape, access model, notification side, storage layout, verb), and the most likely failure mode in implementation is conflating it with Report — a mistake the library specifies guard-rails against in five separate places. This outcome validates the asymmetric wiring: fire-and-forget post-submission semantics ([[Decision - Fire-and-Forget Feedback]]) plus the Discord-as-pickup notification surface ([[System - Feedback Storage & Notification]]) plus IP-logging-for-abuse-protection-only ([[Decision - IP Logging for Abuse Protection]]). Shipping Feedback in MVP — rather than as a follow-up — keeps the two-intake-types identity load-bearing rather than aspirational.
