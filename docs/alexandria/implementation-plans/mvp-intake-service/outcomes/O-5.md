## Validation Criteria

- When the primary Discord webhook POST fails (non-2xx, network error, timeout), the service makes a second webhook call to the same URL whose body carries: an error-text summary of the primary failure, the original `discord-payload.json`, and a sanitized `inputs.json` describing the Feedback metadata (UUIDv7, IP, email, sysinfo, attachments manifest — NOT the message text or attachment bytes).
- If the second webhook call also fails, the service emits a Sentry event tagged with the failure context AND writes a structured CloudWatch log line; no third retry is attempted, no exponential backoff, no queue.
- The first-call failure path does NOT roll back the S3 writes — `feedback.json` + `feedback.txt` + attachments remain on S3 for Triagers to retrieve out-of-band; the Feedback object is the source of truth even when notification fails.
- The second-call payload is recognizably a failure-self-report (distinct embed style, prefix in the title) so Triagers can distinguish it from a normal Feedback notification at a glance in the Discord channel.
- The CLI confirmation returned to the Feedback Submitter is identical regardless of whether notification succeeded — the Submitter has no Discord-failure-aware affordance, consistent with [[Decision - Fire-and-Forget Feedback]].

## Motivation

[[System - Feedback Storage & Notification]] specifies an unusual failure-handling pattern: one retry, but the retry payload is *self-describing* (the second call carries the original payload + inputs + error text), and if that also fails, Sentry is the operational escape hatch. This avoids two failure modes the library names explicitly — silent loss (a Feedback that landed on S3 but no one ever finds out) and exponential-backoff-with-queueing (which would require a queue and reintroduce the topology complexity [[System - Service Topology]] forbids). Tier is Should rather than Must because the happy-path Feedback flow ships without it, but implementing it now keeps the failure semantics fresh in the same code change as the happy path; deferring it risks the failure path getting bolted on later without preserving the no-retry-no-queue posture.
