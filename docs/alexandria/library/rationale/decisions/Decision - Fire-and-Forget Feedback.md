# Decision - Fire-and-Forget Feedback

## WHAT: The Choice

The Feedback flow on `fabro.report` is **strictly fire-and-forget from the Feedback Submitter's perspective**. When `fabro feedback` completes successfully, the CLI prints a short confirmation line and exits. That confirmation is the **entire** post-submission surface available to the Feedback Submitter. There is no URL returned, no capability token rendered, no Report-Metadata-Page-equivalent hosted by the service, no delete action from the CLI or from any web page, no "my feedback" listing, no email follow-up from the service, and no recovery flow for a submission the Feedback Submitter regrets or mis-typed. The Feedback Submitter's involvement with the service ends at the moment the CLI exits; the service proceeds to write S3 objects and push the Discord notification without any further interaction with them.

The load-bearing phrasing is *nothing post-submission; the confirmation is the whole contract*. An agent reading this card should not come away believing "fire-and-forget is the v1 access model and we'll add a capability URL or a delete affordance later when it matters." Post-submission submitter-facing surface will not be added later; adding one is permanently out of scope under [[Principle - Narrow Forever]]. Fire-and-forget is forever.

**Scope:** this Decision applies to the Feedback flow only. The Debug Bundle flow has a different access model — capability URLs grant view + delete via possession of the URL, governed by [[Decision - Capability URLs over Auth]]. A9 and A19 are **inverse-shape Decisions**: A9 chooses capability-URL access *over* auth on the Debug Bundle flow (the Debug Bundle flow has a post-upload surface — the Report Metadata Page — that needs gating, and the access model for that surface is URL possession); A19 chooses no access model at all on the Feedback flow (the Feedback flow has no post-submission surface to gate in the first place, so no access-control layer is needed). Both Decisions honor [[Principle - Narrow Forever]]'s identity-free, no-account-concept commitment, but through different mechanisms appropriate to each flow's structural shape. The pairing is deliberate and is the access-model expression of the 2026-04-23 two-intake-types-forever identity.

## WHERE: Ecosystem

- Governed by:
  - [[Product Thesis - Pickup Point, Not Triage Surface]] — the pickup-point thesis extends across both intake types (per the 2026-04-23 identity update). Feedback is also a pickup — the Feedback Submitter drops a message, the service captures it, the Fabro team picks it up out-of-band through Discord (with optional S3 retrieval). Fire-and-forget is the access-model expression of *the Feedback Submitter's job is to drop, not to manage*; a capability URL or a delete affordance would imply the Submitter has ongoing involvement with the submission, which turns the pickup into a session.
  - [[Principle - Narrow Forever]] — the F6 out-of-scope list includes cross-submission identity tracking across either flow, per-user accounts across either flow, and any post-submission surface that would turn Feedback from a pickup into a conversation. This Decision is the positive choice that makes those rejections concrete at the Decision layer on the Feedback side: if the Feedback Submitter has no account and no identity across submissions, then they have no basis on which a service-side post-submission surface could authorize them, which means any such surface would be either open (unauthorized, available to anyone) or authenticated (requires the account the product refuses to have). Neither is compatible with the narrow-forever commitment. Fire-and-forget resolves the tension by refusing the surface entirely.
  - [[Principle - Strategy Support Effectiveness for Self-Hosted Users]] — Strategy's two-mechanism shape (Debug Bundles carry reproducibility data; Feedback carries voice) is served by each mechanism doing its own job narrowly. Strategy is buying *team retrieval of voice*, not *Feedback Submitter engagement with their submission after sending*. A post-submission surface for the Submitter is polish outside of what Strategy is optimizing for.
- Paired with — inverse-shape for the other flow:
  - [[Decision - Capability URLs over Auth]] — the inverse Decision for the Debug Bundle flow. A9 chose capability URLs because the Debug Bundle flow has a post-upload surface (the Report Metadata Page) where a Reporter needs to see that their upload landed and has the option to delete if they change their mind about sharing. The Feedback flow has no equivalent surface to gate, because the Feedback Submitter has no equivalent need: the Reporter shares a URL out-of-band and can recall its access via delete; the Feedback Submitter sends voice that has already been delivered to Discord by the time the CLI exits, and the Submitter does not need to (and could not, meaningfully) recall something that has already been read by its audience. The two Decisions are **explicitly inverse-paired** — A9 says "capability-URL access over auth"; A19 says "no access model at all, because there is no post-submission surface." Both Decisions are scoped explicitly to their respective flow on each card, so future agents reading either cold can find the scope boundary without inferring it.
- Tonal expression (same register, different shape):
  - [[Principle - Minimal Public Surface Feels Calm]] — the `fabro feedback` CLI confirmation inherits the same "efficient and reassured" register as the Debug Bundle flow's success output. Where the Debug Bundle flow confirms "upload landed, here is the URL to share," the Feedback flow confirms "submission landed, the Fabro team will see it." Both are compact; both step out of the way; both refuse ceremony. The load-bearing difference is that the Feedback flow's confirmation is the *entire* user-facing success surface (no URL to follow, no page to visit), which is why the CLI register carries more of the "reassured" weight for Feedback than it does for Debug Bundles.
- Vocabulary:
  - [[Standard - Noun Vocabulary]] — the **Feedback** canonical definition names "No capability URL, no delete action, no rendered page — the Feedback Submitter's involvement ends at CLI confirmation." The **Feedback Submitter** canonical definition names "no URL is returned, no page is rendered, no delete action is offered." This Decision is the rationale behind both of those vocabulary choices; drift between the Standard's phrasing and this card's phrasing is a defect.
- Related:
  - [[Decision - IP Logging for Abuse Protection]] — A18 names the identity-data-scope commitment; this Decision names the post-submission-access commitment. Together they constrain the Feedback flow's submitter-facing shape: what is captured (optional email + server-logged IP, scoped tightly) and what is returned (a confirmation line, nothing else). Neither Decision has visibility into the other's scope, by design — scope commitments are separate so they can be revisited independently.
  - [[Decision - 30-Day Retention Default]] — A11's 30-day retention applies to Feedback (extended 2026-04-23 to cover both intake types). The Feedback Submitter's inability to delete is paired with the mechanism by which Feedback disappears from the service's storage: the S3 lifecycle rule deletes every Feedback at the 30-day boundary. The interaction-layer expression of this coupling — *Feedback is permanent from the Submitter's perspective and expires only via the 30-day S3 lifecycle rule* — is [[Standard - Interaction Patterns (CLI + Delete)]]'s "No Delete on the Feedback Flow" subsection.
- Referenced by:
  - [[Agent - Feedback Submitter]] — the persona card's "post-submission surface is nothing" property inherits directly from this Decision; the Feedback Submitter's narrow shape is the role-layer expression of fire-and-forget.
  - [[Component - Feedback]] — the Feedback entity's no-URL, no-rendered-page, no-delete-action structural properties inherit from this Decision; the Component card's lifecycle (created at submission → optionally read by Triagers → auto-deletes at retention deadline) has no Feedback-Submitter-facing step because this Decision rules one out.
  - [[Component - Report Metadata Page]] — A4 cites this Decision as the counterpart-entity asymmetry: the Debug Bundle flow has exactly one rendered page (this Metadata Page), and the Feedback flow has none, because Feedback is fire-and-forget. The asymmetry is visible at the rendered-surface layer and traces back to this Decision.
  - [[Standard - Interaction Patterns (CLI + Delete)]] — A7's "No Delete on the Feedback Flow" subsection carries the load-bearing phrasing that the Feedback Submitter has no recall mechanism at the interaction layer; this Decision is the upstream rationale A7 defers to.
  - [[Standard - Information Architecture]] — A6's IA shape names that the Feedback flow has no page, no URL, no listing, no routable address on the service; this Decision is the access-model half of that IA commitment.
- Implemented by:
  - [[System - Feedback Storage & Notification]] — A17 is the mechanism that honors this Decision at the protocol layer: no capability URL is minted, no `GET /v1/feedback/:id` endpoint exists, no `DELETE /v1/feedback/:id` endpoint exists, no rendered-page route exists. The absence of those mechanisms is load-bearing, enforced by the Fargate service's route table simply not including them.
- Stack dependency:
  - [[Decision - Service Stack]] — the AWS-native Rust-on-Fargate stack has no coupling to this Decision beyond the general property that the service's code determines its surface. No capability of the stack forces or prevents fire-and-forget; the Decision is implemented by choosing not to implement the contrary routes.
- Observability boundary:
  - [[Decision - Sentry for Service Errors, Not Bundle Processing]] — Sentry context respects the fire-and-forget posture: if a `POST /v1/feedback` request fails in ways that trigger Sentry, the Feedback Submitter is not shown a Sentry event ID, a Sentry dashboard link, or a "please report this crash" affordance. The Reporter-facing error register from [[Principle - Minimal Public Surface Feels Calm]] carries the Submitter-facing failure surface; Sentry is operational-internal, not Submitter-facing.

## WHY: Rationale

### Options Considered

- **Option A (rejected): Return a capability URL on `fabro feedback` success, parallel to the Debug Bundle flow.** The Feedback Submitter gets a `fabro.report/f/<id>` URL on success; possession of the URL grants view of a Feedback Metadata Page (showing Feedback ID, timestamp, message excerpt, delete button) and the ability to delete the submission. Rejected for three converging reasons:
  1. **It implies a page exists to visit.** A capability URL presupposes a rendered surface; rendering a Feedback Metadata Page means designing page content, accessibility posture, tone register, and visual direction for a surface the Feedback flow is structurally designed not to need. Every one of those is a new design commitment whose cost compounds with the rest of the product.
  2. **It implies a team-facing surface on the service.** Once a capability URL exists and a page renders at it, the next natural extension is a team-facing view: "let Triagers see a list of recent Feedbacks" or "show the Fabro team which Feedbacks have been viewed." Both are exactly the team-dashboard drift [[Principle - Reject Like bun.report Drift]] names and [[Principle - Narrow Forever]] rules out across both flows.
  3. **Feedback Submitters do not have the Reporter's "I want to delete this bundle I just shared" concern.** Reporters share a capability URL out-of-band (GitHub issue, Slack, email), which means the URL may land somewhere the Reporter later wishes it hadn't; delete-on-URL-possession is the mitigation. Feedback Submitters do not share the submission out-of-band; the submission is delivered to Discord by the service, not by the Submitter, so the Submitter has no "I accidentally shared this in the wrong place" scenario to remediate. The primary use case for a delete action does not apply.
- **Option B (rejected): Return a reference-only ID the Feedback Submitter could cite in follow-up correspondence.** No capability URL, no page, no delete — but the CLI prints a short ID (e.g., the UUIDv7, or a truncated form) so the Submitter could say "about feedback abc123, …" in out-of-band communication with the Fabro team. Rejected because a reference-only ID still creates a follow-up flow: the Submitter says "about abc123," the team looks up abc123 (which requires a triage-surface shape, even if internal), and the pickup turns into a conversation. The `fabro.report` service is not a ticketing system; a reference-only ID is the lightest possible version of a ticket, which is the wrong direction for a pickup point. Additionally, the UUIDv7 is in the Discord post footer and in `feedback.json`; if the team needs to refer to a specific Feedback in out-of-band communication, they can find the ID themselves without it being surfaced to the Submitter.
- **Option C (rejected): Return nothing at all — silent success.** The CLI succeeds with exit code 0 and prints no output at all. Rejected because silent success violates [[Principle - Minimal Public Surface Feels Calm]]'s "efficient *and* reassured" anchor. A Feedback Submitter who types `fabro feedback "important bug report"` and sees the terminal return to the prompt with no confirmation has no way to distinguish "submission succeeded silently" from "CLI is broken and swallowed the input silently." The register specifically rejects silent return precisely because it erodes the *reassured* half of the anchor. The CLI must confirm; the question this Decision answers is what the confirmation contains, not whether it exists.
- **Option D (rejected): Return an email-based confirmation.** If the Submitter passed `-e, --email`, the service sends a confirmation email. Rejected because the service does not send outbound email; adding an outbound-email dependency is a scope expansion under [[Principle - Narrow Forever]] (new third-party dependency beyond Discord, per [[System - Service Topology]]'s "third-party egress is strictly bounded" property), and because email confirmation is itself a post-submission affordance — it implies the service tracks the submission and can reach the Submitter afterwards, which is the account-shaped posture the product refuses.
- **Option E (chosen): Fire-and-forget. The CLI prints a confirmation line on success (in the "efficient and reassured" register per [[Principle - Minimal Public Surface Feels Calm]]). No URL. No ID visible to the Submitter. No page. No delete. No email. The Submitter's involvement ends at the confirmation.** Chosen because it matches the Feedback flow's structural shape: the submission is already in Discord and S3 by the time the CLI exits; the Submitter has no legitimate post-submission operation to perform; giving them an affordance for operations they do not need either introduces surface area (Option A, Option B, Option D) or erodes reassurance (Option C). Fire-and-forget is the shape where each of those trade-offs lands correctly.

### What Drove the Choice

Two structural facts determined the shape of this Decision.

First, **the Submitter's work is done at the moment the CLI exits**. Debug Bundle uploads produce a URL that the Reporter then shares out-of-band — the URL is the instrument of the Reporter's *continuing* work (sharing with the team, potentially deleting later). Feedback submissions are delivered to their audience (the Fabro team, via Discord) by the service itself — there is no remaining work the Submitter needs a handle on. A capability URL for a Feedback would be an affordance for operations the Submitter has no use for.

Second, **every post-submission surface is a drift vector**. A capability URL implies a page; a page implies content design, tone, accessibility posture, and a team-facing extension; a delete affordance on the page implies submission ownership, which implies identity, which implies accounts. The cleanest way to prevent the drift cascade is to refuse the first link in the chain. Fire-and-forget is that refusal.

The F3 drift list (per [[Principle - Reject Like bun.report Drift]]) already names "post-upload feedback on the Debug Bundle flow" as a drift shape — the pattern where `bun.report` attaches a "how was this bundle?" survey to the post-upload experience. This Decision extends the same logic to the Feedback side: any Submitter-facing surface that invites continued engagement with a submission after submission is the same drift shape in a different flow's clothing, and is rejected on the same grounds.

### What It Costs

- **No recall for a regretted submission.** A Feedback Submitter who types a message in frustration and immediately regrets the tone has no way to recall the submission through the service. The submission is already in Discord and S3 by the time the CLI exits. The correct recourse is an out-of-band request to the Fabro team; the team can manually delete the S3 objects if the request is legitimate. Accepted because the alternative (a Submitter-facing delete capability) requires a capability URL or an identity-bound authorization, both of which are scope expansions beyond what this Decision and [[Principle - Narrow Forever]] tolerate. The Submitter is trading a narrow-and-final submission model for a more nuanced recall model, and the product choice is the narrow one.
- **No "view my submission" for the Submitter.** A Feedback Submitter who wants to confirm exactly what text was sent (beyond the confirmation line) must check their terminal history or their text editor; the service is not the memory of their submission. Accepted because the alternative (a view page) requires a capability URL and a rendered surface, both of which are scope expansions. Additionally, the Submitter wrote the text — the service is an intake, not a canonical-memory service.
- **No "my submissions" listing across submissions.** A Feedback Submitter who wants to see their submission history on the service has no way to do so. Accepted because listing requires Submitter identity (account, login, persistent session), which is out of scope by [[Principle - Narrow Forever]] for both flows.
- **No team-facing view of recent Feedbacks hosted on the service.** A Triager who wants to browse recent Feedbacks reads Discord or uses their own AWS credentials against the S3 `feedback/` prefix — exactly the shape [[Agent - Triager]]'s Feedback workflow describes. Accepted because any team-facing view hosted on the service is the team-dashboard drift rejected across both flows by [[Principle - Narrow Forever]] and [[Principle - Reject Like bun.report Drift]]. This is a benefit of fire-and-forget, not just a cost — Submitter-side fire-and-forget structurally rules out the team-facing mirror of the same surface.
- **Abuse-cleanup is an out-of-band operation, not a service-side capability.** When the Fabro team needs to delete a specific Feedback for abuse or legitimate takedown reasons, they do so with AWS tooling against the S3 object, not via a service endpoint. Accepted because a service-side delete endpoint (even Triager-only) would reintroduce a delete affordance, and the presence of such an endpoint would be visible in the service's code and routing surface even when not used — the kind of structural weight this Decision refuses. AWS IAM-scoped object deletion is the correct mechanism; it is auditable (AWS CloudTrail), it is out-of-band (not service-side), and it requires the Fabro team's own credentials.

### Scope of Applicability

This Decision governs the access model and post-submission surface on `fabro.report`'s Feedback flow — specifically the shape of the `fabro feedback` CLI's return value, the absence of any rendered page for Feedback, the absence of any Submitter-facing retrieval or mutation endpoint for Feedback, and the absence of any service-side delete capability for Feedback.

It does **not** govern:

- **The Debug Bundle flow** — that flow has a different access model, governed by [[Decision - Capability URLs over Auth]]. The scope of each Decision is explicit on both cards; neither extends to the other flow.
- **Out-of-band Fabro team operations** — team members can manually delete S3 objects (for abuse, takedown requests, legitimate deletion on a Submitter's out-of-band request) using their own AWS credentials. This Decision does not constrain what the Fabro team does with its own infrastructure; it constrains what the service offers to Feedback Submitters.
- **Discord's own post lifecycle** — the Fabro team may edit or delete Discord posts in the team channel per Discord's own affordances. That is Discord-side behavior, not service-side.
- **30-day retention** — the S3 lifecycle rule deletes every Feedback at the retention deadline, per [[Decision - 30-Day Retention Default]] (extended 2026-04-23 to cover both flows). Retention is a mechanism separate from this Decision; fire-and-forget is about the absence of Submitter-facing post-submission operations, not about how long the submission lives on the service.

### Conditions That Would Trigger Revisiting

Because post-submission submitter-facing surface is on [[Principle - Narrow Forever]]'s permanently-out-of-scope list for the Feedback flow, revisiting this Decision requires reopening that Principle as an identity change, not treating this as an implementation detail. Specifically:

1. **The product owner explicitly decides to add a Submitter-facing post-submission surface to the Feedback flow, in writing, in a source-material update.** This is an identity change for the product under the framing of [[Principle - Narrow Forever]] — the Feedback flow's shape would be re-specified, and the accompanying changes to [[Agent - Feedback Submitter]], [[Component - Feedback]], [[System - Feedback Storage & Notification]], and [[Standard - Interaction Patterns (CLI + Delete)]] would cascade from it.
2. **A systematic pattern of Submitter regret or abuse-mitigation need that out-of-band channels cannot handle.** If the Fabro team observes recurring submission-regret patterns that a case-by-case out-of-band process cannot address, the product owner might decide a Submitter-facing delete affordance is worth the scope cost. Today, no such pattern exists.
3. **An audience change under [[Decision - Who This Service Is For]].** If the audience widens to populations with different expectations (e.g., hosted-Fabro users with an existing identity system and different retention expectations), the access-model defaults could shift and this Decision would be revisited alongside C4 and [[Decision - Capability URLs over Auth]].
4. **A security or abuse pattern that the "submit in Discord and S3 immediately, no recall" model cannot defend against.** Today, the service has failure self-reporting ([[System - Feedback Storage & Notification]]) and IP logging ([[Decision - IP Logging for Abuse Protection]]) as the operational-resilience substrate. If these prove insufficient in a way that a Submitter-facing recall would help address, the model could need revisiting. No such pattern exists today.

None of those conditions exist today. This Decision is stable.

## HOW: Application

### Following This Decision

- `fabro feedback` succeeds by printing a confirmation line (per [[Standard - Interaction Patterns (CLI + Delete)]]'s `fabro feedback` register) and exiting. The confirmation does not contain a URL, a Feedback ID, or any token the Feedback Submitter could later use to reference the submission on the service.
- The service's HTTP route table for the Feedback flow contains exactly one route: `POST /v1/feedback`. There is no `GET /v1/feedback/:id`, no `DELETE /v1/feedback/:id`, no `PATCH /v1/feedback/:id`, no `/f/:id` rendered page. The absence of these routes is enforced by not implementing them.
- Feedback Submitters who want a record of what they sent maintain one themselves (terminal history, their own notes, a local editor buffer). The service is not the canonical memory of the submission's content.
- Feedback Submitters who want to recall a submission contact the Fabro team out-of-band (via the optional email they attached, via Discord if they are a channel member, via another channel). The Fabro team manually deletes the S3 objects using their own AWS credentials if the request is legitimate. The service itself offers no recall mechanism.
- Triagers read Feedback via the Discord post (primary surface, per [[Agent - Triager]]'s Feedback workflow) and optionally retrieve the full Feedback from S3 using their own AWS credentials (secondary surface). Neither path traverses any Submitter-facing affordance; the Submitter's fire-and-forget posture is symmetric with the Triager's S3-direct posture in that neither side uses a service-hosted post-submission surface.

### Violating This Decision

- **Wrong:** Returning a capability URL from `fabro feedback` on success, as a "view your feedback here" affordance. Violates the fire-and-forget commitment and re-introduces a post-submission submitter-facing surface the flow is designed not to have. See [[Standard - Interaction Patterns (CLI + Delete)]]'s anti-example list.
- **Wrong:** Implementing a `DELETE /v1/feedback/:id` endpoint and exposing it as a CLI subcommand (`fabro feedback delete <id>`) or a link in the Discord post. Re-introduces delete as a submitter-facing service capability, which is the exact shape this Decision refuses.
- **Wrong:** Implementing a `GET /v1/feedback/:id` endpoint for *any* consumer (Submitter-facing, Triager-facing, or general). Triagers retrieve via their own S3 credentials; Submitters have no retrieval affordance. A GET endpoint is a team-dashboard or Submitter-view shape, both of which are drift per [[Principle - Narrow Forever]] and [[Principle - Reject Like bun.report Drift]].
- **Wrong:** Sending an outbound email to the Feedback Submitter's optional email on successful submission ("your feedback has been received"). Reintroduces a post-submission touch from the service to the Submitter; the service is not a transactional-email system, and outbound email is a new third-party dependency beyond what [[System - Service Topology]]'s "third-party egress is strictly bounded" property tolerates.
- **Wrong:** Printing the UUIDv7 (or any form of the Feedback's ID) in the CLI confirmation. Even as a reference-only ID, the number creates a follow-up flow and implies the Submitter might need the identifier for later correspondence; the flow is designed so the Submitter never needs it.
- **Wrong:** Returning silent success (no confirmation line, exit code 0 only). Violates the *reassured* half of [[Principle - Minimal Public Surface Feels Calm]]'s register. Fire-and-forget is about what the confirmation *does not contain* (URL, ID, delete affordance), not about the absence of the confirmation itself.
- **Wrong:** Surfacing a Sentry event ID to the Submitter on a failed `POST /v1/feedback` request ("this failed; please reference event abc123 when contacting support"). Sentry is operational-internal per [[Decision - Sentry for Service Errors, Not Bundle Processing]]; a Sentry-linked error output both widens the Submitter's post-submission surface and introduces the support-SLA anti-goal posture [[Principle - Strategy Support Effectiveness for Self-Hosted Users]] rules out.

### Test

Before adding any CLI output, HTTP route, external notification, or service-side state machine that involves a Feedback after submission, ask three questions in order.

First: "Does this feature give the Feedback Submitter any affordance beyond the CLI confirmation line?" If yes — a URL, an ID, an email confirmation, a page, a delete action, a view endpoint — the feature violates fire-and-forget. Reject or escalate.

Second: "Does this feature depend on the service tracking the Submitter as a persistent identity across or within submissions?" If yes — a session, an account, a cookie, a persistent token — the feature violates the identity-free commitment this Decision inherits from [[Principle - Narrow Forever]].

Third: "Does this feature create a team-facing or Submitter-facing surface hosted by the service for the Feedback flow?" If yes — a view page, a listing endpoint, a delete affordance, a dashboard — the feature is drift under [[Product Thesis - Pickup Point, Not Triage Surface]]'s extended-to-both-flows coverage. Reject.

A second-order test: "Could I implement this feature by removing the 'no URL is returned' property from the CLI?" If yes, the feature is a URL-based extension that fire-and-forget rules out.
