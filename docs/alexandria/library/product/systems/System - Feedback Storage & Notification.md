# System - Feedback Storage & Notification

## WHAT: Definition

The **data-and-notification-topology system for the Feedback flow** — the card that gives `fabro.report`'s Feedback intake its storage, notification, and failure-reporting mechanics. One S3 prefix for persistence, one Discord webhook for team notification, one self-reporting path when the webhook fails, one lifecycle rule aligned with [[Decision - 30-Day Retention Default]] — each chosen so that the policy commitments made in [[Decision - Fire-and-Forget Feedback]], [[Decision - IP Logging for Abuse Protection]], and [[Decision - 30-Day Retention Default]] are enforced structurally rather than by application convention. Specifically: the same S3 bucket as Debug Bundles (`fabro-report-bundles`, env-overridable) in `us-east-1` (env-overridable), under a distinct `feedback/` prefix; per-Feedback directories of the form `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/` containing `feedback.json` (envelope metadata), `feedback.txt` (message text, when present), and optional `attachments/<filename>` objects; a Discord webhook push using Discord's component-v2 payload pattern (webhook URL held in `FEEDBACK_DISCORD_WEBHOOK_URL` via Secrets Manager / SSM Parameter Store); a failure-self-reporting path that retries the webhook call with error details and diagnostic files when the primary call fails; and a Terraform-declared S3 lifecycle rule that expires every object under the `feedback/` prefix 30 days after creation.

This System card is paired with [[System - Debug Bundle Retention, Storage, and Key Scheme]] — A5 owns the **data** topology for the Debug Bundle flow (one bucket, one key scheme, 32-hex-char IDs, presigned-URL upload path, sidecar metadata). This card owns the **data-and-notification** topology for the Feedback flow (same bucket, different key scheme, UUIDv7 IDs, direct-POST upload path, Discord push, failure self-reporting). The bucket is shared at the bucket level — one bucket, two top-level prefixes — but the key schemes, ID shapes, object layouts, upload paths, and (for Feedback) notification side are flow-specific and live in separate System cards. This card is also paired with [[System - Service Topology]] — A14 owns the operational topology both data systems run on (Fargate, Route53, IAM, secrets, Terraform, Discord webhook *as an egress*); this card owns the Feedback-specific data-and-notification mechanics that Fargate executes.

## WHERE: Ecosystem

- Policy anchors (mechanism-for):
  - [[Decision - Fire-and-Forget Feedback]] — names the no-URL, no-page, no-delete commitment. This System card is the mechanism that makes the commitment structurally enforceable: no capability URL is minted on submission (the service returns only a confirmation line per [[Standard - Interaction Patterns (CLI + Delete)]]); no rendered page exists because no endpoint serves one; no delete action exists because no `DELETE /v1/feedback/:id` route is implemented. The absence of those mechanisms is load-bearing.
  - [[Decision - IP Logging for Abuse Protection]] — names the scope commitment for IP capture. This System card is the mechanism that honors it: the client IP is written into `feedback.json` at submission time, retained for 30 days (same as every other Feedback field), and never surfaced through the service for any purpose beyond abuse-protection investigation. No analytics emission, no cross-submission join, no geolocation lookup, no export path beyond the S3 object the Triager reads with their own AWS credentials.
  - [[Decision - 30-Day Retention Default]] — names the 30-day commitment across both intake types. This System card is the mechanism that enforces it on the Feedback side: an S3 lifecycle rule with `expiration.days = 30` applied to every object under the `feedback/` prefix, declared in Terraform (alongside the Debug Bundle lifecycle rule declared by [[System - Debug Bundle Retention, Storage, and Key Scheme]]), runs server-side inside S3 with no cron and no application-side sweeper.
- Entities stored:
  - [[Component - Feedback]] — the first-class entity whose fields this System's storage representation persists. The Feedback's UUIDv7 appears as `<uuidv7>` in the key scheme; `feedback.json` carries the structured envelope (IP, email, Fabro version / platform / arch, timestamp, retention deadline, file attachments manifest); `feedback.txt` carries the message text when present; `attachments/<filename>` objects carry the attached files. The Feedback (the Component) names the envelope; this System names the objects that hold the envelope.
- Roles that traverse this System:
  - [[Agent - Feedback Submitter]] — submits by `POST /v1/feedback` through the Fargate service. Their CLI sees only the confirmation line; the S3 writes and the Discord push happen server-side without any Feedback Submitter-facing surface. The `email` field on the Feedback is captured from the CLI (if `-e, --email` was passed) and appears as the Discord post header.
  - [[Agent - Triager]] — reads Feedback via the Discord post pushed by this System (primary surface) and optionally retrieves the full Feedback from S3 using their own AWS credentials (secondary surface, same IAM principal as Debug Bundle retrieval, separate from the Fargate task role that writes). The Discord post carries the header, sysinfo, message body, attachments tree, and footer; S3 is the authoritative persistence. See A17's Discord payload specification below.

  - [[Standard - Noun Vocabulary]] — "Feedback" is the submission entity (this System's primary payload); the Discord channel is an external notification target, not a first-class noun on the service. The verb asymmetry — Debug Bundles are *uploaded*, Feedbacks are *submitted* — is honored in this System's language: `feedback.json` is written, the Discord post is pushed, the submission is recorded in server logs.

  - [[Decision - Fire-and-Forget Feedback]] — no capability URL is minted; no rendered page is served; no delete action is exposed. The service's public surface for the Feedback flow consists of exactly one endpoint (`POST /v1/feedback`); that endpoint returns a confirmation and no addressable token.

Discord is a push target, not a service-hosted triage surface. This card is the data-and-notification expression of the pickup-point thesis for the Feedback flow.

## WHY: Rationale

This System card exists because the Feedback flow's data topology is distinct from the Debug Bundle flow's data topology in every specific that matters — different prefix, different ID shape, different upload path, different object layout — *and* because the Feedback flow has a notification side (Discord webhook push + failure self-reporting) that has no analog on the Debug Bundle flow. Collapsing both flows' data topologies into one System card would hide those asymmetries under a Frankenstein abstraction that serves neither flow; collapsing the Feedback data topology and the Feedback notification topology would hide the fact that these are two different concerns with two different reliability profiles (S3 writes are durable and near-always-succeed; Discord webhook calls are best-effort and need failure handling).

The load-bearing claim of this System is that **infrastructure and protocol enforce the commitments**. The 30-day retention is an S3 lifecycle configuration declared in Terraform — S3 executes it server-side, same as for Debug Bundles (per A5's identical mechanism). The fire-and-forget posture is a protocol property: there is no `DELETE` endpoint to call, no capability URL to render, no rendered page to serve, because the Fargate service's route table simply does not include those routes. The IP-logging scope commitment ([[Decision - IP Logging for Abuse Protection]]) is enforced by writing IP only to `feedback.json` and the server log, never to an analytics pipeline, a cross-submission join table, or a geolocation service — a commitment the service honors by not having the code that would violate it.

The secondary load-bearing claim is **Discord is a push target, not a triage surface, and the service self-reports its own webhook failures**. Posting to Discord is a fire-and-forget HTTPS call from the service's perspective too: success produces visible voice for the team; failure triggers a second webhook call carrying the error text plus `discord-payload.json` (the payload the first call attempted) and `inputs.json` (the request payload), so that the Fabro team sees the failure in the same channel they would have read the successful post in. The service does not retry the original post content (which might itself be the failure mode); it self-reports, which is a different reliability shape — the team gets to see *that* something failed even if the *what* is degraded.

The tertiary load-bearing choice is **direct POST from CLI to service, not presigned S3 URLs**. Debug Bundle tarballs are large (up to 50 MB per [[Standard - Interaction Patterns (CLI + Delete)]]) and the presigned-URL architecture keeps their bytes out of Fargate compute entirely. Feedback payloads are smaller (text + small file attachments; no equivalent hard cap at the Standard layer as of 2026-04-23) and the direct-POST path is simpler — the Fargate task parses the multipart / JSON body, writes the S3 objects itself, and the service's operational posture is unchanged. The choice accepts one extra byte-transit hop (CLI → Fargate → S3, vs. Debug Bundles' CLI → S3 direct) in exchange for simpler code, simpler failure handling, and an IAM path that does not require per-request presigned-URL generation. If payload-size pressure surfaces later, switching to a presigned-URL architecture is a mechanism change to this card, not a policy change.

## HOW: Specification

### S3 Bucket and Prefix

- **Bucket:** `fabro-report-bundles` by default, the same bucket [[System - Debug Bundle Retention, Storage, and Key Scheme]] uses. Env-overridable. Shared at the bucket level; distinct at the prefix level.
- **Prefix:** `feedback/` — all Feedback objects live under this top-level prefix. The Debug Bundle flow uses no `feedback/` segment (Debug Bundle objects live at `<YYYY>/<MM>/<DD>/<id>/` under the bucket root); the two flows are unambiguously separable by prefix.
- **Region:** `us-east-1` by default, env-overridable, matching the Debug Bundle flow.
- **Access model:** private bucket. Public read is **not** enabled. The Fargate task has write access via its IAM role ([[System - Service Topology]] owns the role); Triagers read directly using their own AWS credentials (per [[Agent - Triager]] Workflow 2). No public S3 URL for a Feedback object; the Discord post may include an S3 link that a Triager follows, but that link resolves only under AWS IAM for the Triager's credentials, not via anonymous access.

### Key Scheme

- **Pattern:** `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/<object>` where `<object>` is one of:
  - `feedback.json` — the structured envelope metadata (always present).
  - `feedback.txt` — the message text (present when the Feedback Submitter provided text, absent when the submission is attachment-only).
  - `attachments/<filename>` — one object per attached file, in an `attachments/` subdirectory under the Feedback's UUIDv7 prefix (present when the Feedback Submitter attached files, absent otherwise).
- **Date partition:** daily, matching [[System - Debug Bundle Retention, Storage, and Key Scheme]]'s granularity. `<YYYY>/<MM>/<DD>` derives from the submission timestamp.
- **`<uuidv7>`:** the Feedback's UUIDv7 ID in its canonical string form (lowercase hex, hyphens, e.g., `018f2e7c-3a4b-7000-8000-111122223333`). UUIDv7's time-ordering property makes chronological S3 listing within a day coherent (`aws s3 ls s3://fabro-report-bundles/feedback/2026/04/23/` lists a day's Feedbacks in approximately time order).
- **Properties this layout guarantees:**
  - A Feedback's metadata (`feedback.json`), message (`feedback.txt`), and attachments share one prefix, so the lifecycle rule expires them together (no orphan envelope, no orphan messages, no orphan attachments).
  - Single-Feedback manual deletion (for abuse cleanup or out-of-band takedown requests from the Fabro team) is a prefix delete, atomic at the Feedback level.
  - Date-partition browsing enables Triager-side chronological review via AWS tooling (`aws s3 ls s3://fabro-report-bundles/feedback/<YYYY>/<MM>/<DD>/`).
  - The `feedback/` top-level prefix cleanly separates Feedback storage from Debug Bundle storage inside the same bucket, which keeps the shared-bucket IAM policy boundaries clear and prevents cross-flow accidental object touches.

### Object Shapes

- **`feedback.json`** — the structured envelope. At minimum includes: `id` (UUIDv7), `timestamp` (submission moment, ISO 8601), `ip` (server-captured client IP), `email` (optional, from `-e, --email`), `fabro_version`, `platform`, `arch`, `retention_deadline` (`timestamp + 30 days`), and `attachments` (a manifest array of `{filename, size, content_type}` per attached file; empty when no attachments). Implementation-level extensions are allowed if consistent with [[Standard - Noun Vocabulary]]'s Feedback entry; this Standard does not enumerate every possible implementation field.
- **`feedback.txt`** — the message text as the Feedback Submitter supplied it (from the positional argument, from stdin, or absent). Plain UTF-8. Not wrapped, not modified, not parsed on the service side.
- **`attachments/<filename>`** — the file bytes as the Feedback Submitter uploaded them. Filename preserved from the Feedback Submitter's invocation, with implementation-level sanitization where security requires (e.g., rejecting path-traversal sequences). Content type is a metadata field on `feedback.json`'s attachment manifest, not inferred from the object itself here.

### Upload Path (Direct POST to Fargate)

Distinct from the Debug Bundle flow's presigned-URL architecture (per [[Standard - Interaction Patterns (CLI + Delete)]]'s "Upload Architecture" section).

1. The CLI makes an HTTPS `POST /v1/feedback` request to the Fargate service (same Route53 endpoint as the Debug Bundle flow per [[System - Service Topology]]). The request body carries the Feedback payload: message text (if any), file attachments (if any), email (if `-e, --email` was passed), and the Fabro version / platform / arch metadata. Exact wire format (multipart form vs. JSON envelope with base64-encoded files vs. other) is an implementation detail consistent with Fargate's request-handling stack; this Standard does not pin it.
2. The Fargate task parses the request body, generates a UUIDv7, constructs the S3 key prefix from the current date and the UUIDv7, and writes `feedback.json` + `feedback.txt` (if text was provided) + `attachments/<filename>` objects (if files were attached) to S3 via its IAM role.
3. The Fargate task constructs the Discord payload (see below) and posts it to the Discord webhook URL (held in `FEEDBACK_DISCORD_WEBHOOK_URL` via Secrets Manager / SSM Parameter Store per [[System - Service Topology]]).
4. The Fargate task emits a structured server-log line (UUIDv7, timestamp, IP, submission size, attachment count) to stdout. CloudWatch captures it per A14's observability stack.
5. The Fargate task returns a confirmation response to the CLI. The CLI prints the confirmation line per [[Standard - Interaction Patterns (CLI + Delete)]]'s `fabro feedback` register. No URL is returned.

The service is synchronous end-to-end through these steps by default: the CLI waits for the confirmation, which the service does not emit until the S3 writes and the Discord post have completed (or failed and self-reported — see below). There is no background-worker pattern, no queue, no deferred-processing mode. Synchrony is a deliberate simplicity choice consistent with [[Principle - Narrow Forever]]'s minimal-topology commitment ([[System - Service Topology]]'s "No message queue, no cache, no sidecar container" property).

### Discord Webhook (Notification Side)

- **Webhook URL:** held in `FEEDBACK_DISCORD_WEBHOOK_URL` via Secrets Manager / SSM Parameter Store, injected into the Fargate task as an environment variable at task-start time (standard A14 pattern). The URL itself is the authentication (Discord's webhook model); no Discord OAuth, no bot user, no secondary Discord credential.
- **Payload shape:** uses Discord's **component-v2** payload pattern, modeled on `bun.report`'s backend `sendToDiscord` implementation. The payload structure is:
  - **Header:** `## <email>` if the Feedback Submitter provided an email via `-e, --email`; a neutral placeholder (e.g., `## (no email provided)`) otherwise. Exact neutral-placeholder wording is an implementation-level choice consistent with [[Principle - Minimal Public Surface Feels Calm]]'s register applied to Discord post copy.
  - **Sysinfo one-liner:** `Fabro v<version> <platform> <arch>` — a single line identifying the Fabro binary that produced the submission. Always present.
  - **Message body:** the `feedback.txt` content, if present. Absent (or placeholder) for attachment-only submissions.
  - **File attachments tree:** an ASCII-list rendering of the first 20 attachment filenames with "… and N more" suffix when more than 20 files were attached. Structural visibility into what the Feedback Submitter sent, without requiring Discord to display every file inline.
  - **Footer:** the Feedback's UUIDv7, optionally the server-logged IP (shown to Triagers reading the Discord channel; used for abuse-pattern awareness per [[Decision - IP Logging for Abuse Protection]]), and an S3 link to the Feedback's object prefix (`s3://fabro-report-bundles/feedback/<YYYY>/<MM>/<DD>/<uuidv7>/`) or a presigned URL when the implementation chooses to render one. Exact footer wording follows [[Principle - Minimal Public Surface Feels Calm]]'s register.
- **Attached tarball (optional):** if the Feedback includes file attachments and the total attachment size fits within Discord's webhook upload limit (typical ~25 MB), the service may construct a tarball of the attachments and attach it to the Discord message itself, so Triagers can pull attachments inline without touching S3. When attachments exceed Discord's upload limit, the tarball is **skipped** (the attachments tree still lists them, and the S3 link in the footer remains the retrieval path for the full content). No silent truncation of individual files; the service either attaches the full tarball or attaches none.
- **Rate-limit awareness:** Discord webhooks have rate limits (flagged in `bun.report`'s implementation notes as a concern). This System does not implement a per-IP soft rate limit as of 2026-04-23; abuse protection is deferred to [[Decision - IP Logging for Abuse Protection]]'s logging-for-investigation scope. If abuse patterns emerge that overwhelm the Discord webhook despite IP logging, a per-IP rate limit may be added later as a mechanism change to this card (not a policy change to A18).

### Failure Self-Reporting (Discord Webhook Reliability)

When the primary Discord webhook call fails (any non-2xx response, any network error), the service makes a **second webhook call** carrying the error text and diagnostic payloads. The shape is:

1. Primary post fails.
2. The service constructs a second Discord webhook payload with:
   - Header: a failure-notice marker (e.g., `## ⚠️ webhook failure` or similar, register calibrated per [[Principle - Minimal Public Surface Feels Calm]]).
   - Body: the error text (HTTP status, error message, truncated as needed).
   - Attached files:
     - `discord-payload.json` — the payload the first call attempted (so the team can see *what* failed).
     - `inputs.json` — the incoming `POST /v1/feedback` request payload (so the team can reconstruct the Feedback independent of the S3 object).
3. The service POSTs the second payload to the same webhook URL.
4. If the *second* call also fails, the service emits a Sentry event (per [[Decision - Sentry for Service Errors, Not Bundle Processing]]) and logs the failure to CloudWatch. No third retry; the service accepts that both channels are temporarily failing and lets the S3 object stand as the authoritative record.

The load-bearing property of failure self-reporting is **visibility without silent failure**. The team sees that something went wrong in the same Discord channel they would have read a successful post in; they do not have to cross-reference Sentry or CloudWatch to notice the failure. The trade-off is that a persistent Discord outage will produce repeated failure notices; the service does not dedupe these or back off beyond the two-attempt pattern (primary + self-report) per submission. If this trade-off becomes noisy in practice, refinement is a mechanism change.

### Retention Mechanism

- **Mechanism:** S3 lifecycle rule declared in Terraform (`expiration.days = 30`) applied to every object under the `feedback/` prefix. S3 enforces the deadline server-side.
- **No cron. No application-side sweeper.** Same pattern as [[System - Debug Bundle Retention, Storage, and Key Scheme]]. Infrastructure enforces the retention commitment (per [[Decision - 30-Day Retention Default]]).
- **Scope of expiration:** every object under `feedback/`. Because all objects for a given Feedback share the same creation day (they are written synchronously during the `POST /v1/feedback` request handling), they expire on the same day under the same rule.
- **At expiration:** `feedback.json`, `feedback.txt`, and any `attachments/...` objects for a Feedback are deleted from S3. The Feedback is no longer retrievable from the service's storage. The Discord post in the team channel is not affected by this service's expiration — Discord's own retention governs the post's lifetime, and a Triager who wants a long-term record extracts it from Discord or copies the S3 objects before the 30-day deadline.

### Anti-Examples (What This System Is Not)

- **Wrong:** Returning a capability URL on `POST /v1/feedback` success so Feedback Submitters can "see their submission." Forbidden by [[Decision - Fire-and-Forget Feedback]]. The confirmation line is the whole Feedback-Submitter-facing output; no URL, no endpoint, no page.
- **Wrong:** Implementing a `DELETE /v1/feedback/:id` endpoint, even "only for abuse cleanup." Out-of-band Fabro-team deletion happens via AWS tooling against S3 directly (same mechanism that removes abusive Debug Bundles, if needed), not via a service endpoint. A service-side delete endpoint reintroduces the post-submission surface the Feedback flow refuses.
- **Wrong:** Implementing a `GET /v1/feedback/:id` endpoint for Triagers to browse submissions. Forbidden by [[Product Thesis - Pickup Point, Not Triage Surface]]; Triagers read via Discord and optionally via their own S3 credentials. A Triager-facing GET endpoint is the team-dashboard drift shape [[Principle - Narrow Forever]] names as permanently out of scope.
- **Wrong:** Using presigned S3 URLs for Feedback uploads instead of direct POST. The presigned-URL architecture is calibrated for the Debug Bundle flow's larger payload profile (up to 50 MB); Feedback payloads are smaller and direct POST is simpler. Changing to presigned URLs for Feedback is a mechanism-level refactor to this card if payload pressure justifies it, not a neutral implementation choice.
- **Wrong:** Writing the IP to a second persistence layer beyond `feedback.json` + the CloudWatch server log. Forbidden by [[Decision - IP Logging for Abuse Protection]]'s scope commitment; any cross-submission IP index, any analytics emission, any geolocation lookup is a violation of A18.
- **Wrong:** Adding a second notification target (email digest, Slack webhook, SMS, pager) alongside Discord. One notification target per intake type is the current shape; adding a second is a scope expansion under [[Principle - Narrow Forever]]. Similarly, changing the Discord target (e.g., per-topic channels based on Feedback classification) is a scope change, not a mechanism change.
- **Wrong:** Retrying the primary Discord webhook call multiple times before self-reporting. The failure-self-reporting path is "primary fails → self-report fires once → if self-report fails, emit Sentry." No exponential backoff, no queueing. The service accepts that transient Discord failures produce a self-report; the self-report's existence is the notification-reliability commitment.
- **Wrong:** Deduping Feedbacks by content hash or by `(email, message)` fingerprint. Feedback dedup is not a question anyone asks (see [[Component - Feedback]] anti-examples); two identical messages from two Feedback Submitters (or one Feedback Submitter at different moments) are two distinct Feedbacks, each with its own UUIDv7 and its own S3 objects.
- **Wrong:** Storing the `FEEDBACK_DISCORD_WEBHOOK_URL` value in source control, in the Docker image, or in the Terraform state in plaintext. Secrets Manager / SSM Parameter Store is the authoritative secret store per [[System - Service Topology]]; the Terraform repository references the secret's ARN, never the URL value itself.

### Test

Before changing the key scheme, object layout, Discord payload shape, failure-self-reporting behavior, or retention mechanism, ask three questions in order. First: "Does the proposed change preserve every commitment in [[Decision - Fire-and-Forget Feedback]], [[Decision - IP Logging for Abuse Protection]], and [[Decision - 30-Day Retention Default]]?" If any commitment is weakened, the change is a policy change and goes to the product owner through the relevant Decision card, not a mechanism tweak to this System. Second: "Does the proposed change preserve [[Principle - Narrow Forever]]'s minimal-topology commitment — one S3 prefix, one Discord webhook, one retention rule, one failure-self-reporting path?" If the change introduces a new notification target, a new persistence layer, a new retention tier, or a new post-submission endpoint, the minimal-topology commitment is broken. Third: "Does the proposed change preserve the asymmetry with [[System - Debug Bundle Retention, Storage, and Key Scheme]] — different prefix, different ID shape, different upload path, different object layout, plus a notification side A5 has no reason to carry?" If the change would collapse the two Systems' distinctions, the two-intake-types-forever commitment at the data layer is eroded.
