# Component - Feedback

## WHAT: Definition

A **Feedback** is the submission event and its storage identity on `fabro.report`'s Feedback flow. It is created when a Feedback Submitter runs `fabro feedback` and the CLI successfully POSTs the submission payload (optional text, optional file attachments, optional email) to the service's `/v1/feedback` endpoint; it exists for a fixed 30-day retention window from that creation moment; it has no capability URL, no rendered page, and no delete action; and at the retention deadline it auto-deletes, its S3 objects are removed, and the submission is no longer retrievable from the service's storage (the Discord post may still exist in Discord's own retention — that is Discord's concern, not this service's). The Feedback carries a fixed set of authoritative fields — UUIDv7 ID, message text (optional), file attachments manifest (optional), email (optional), server-logged client IP, Fabro version / platform / arch, timestamp, retention deadline — and is immutable from the moment the CLI prints its confirmation: there is no modification operation after creation, no deletion operation from the Feedback Submitter's side, and no Feedback Submitter-facing read surface. The [[Standard - Noun Vocabulary]] entry for Feedback is the authoritative definition; this Component card expands that entry with structural detail, lifecycle, storage couplings, and the load-bearing asymmetry with [[Component - Report]], but inherits the exact field list and naming from the Standard.

**Feedback is not a Report, and must not be treated as one.** This is the load-bearing claim of this card, because the library's default entity is the Report, and an agent reading this card while primed by [[Component - Report]] will be tempted to treat Feedback as "a Report with different fields." That reading is wrong and structurally misrepresents the product's two-intake-types-forever identity ([[Principle - Narrow Forever]]). The asymmetries are substantive:

- **ID shape is asymmetric.** A Report's ID is a 32-hex-character 128-bit CSPRNG-generated random value — chosen so capability URLs derived from it are not brute-forceable (per [[Decision - Capability URLs over Auth]] and [[System - Debug Bundle Retention, Storage, and Key Scheme]]). A Feedback's ID is a **UUIDv7** — time-ordered, server-generated, *not* a capability token. UUIDv7 is chosen because the Feedback flow is fire-and-forget ([[Decision - Fire-and-Forget Feedback]]) and has no capability-URL-addressed surface, which means the unguessability property a Report's ID carries is not needed for a Feedback; the time-ordering property UUIDv7 provides is positively useful for Triagers browsing the `feedback/` S3 prefix chronologically.
- **Access model is asymmetric.** A Report is capability-URL-addressed: possession of the URL grants view of the [[Component - Report Metadata Page]] and the ability to delete the Report. A Feedback has no capability URL, no rendered page, and no delete action from the Feedback Submitter's side. The Feedback Submitter's involvement ends at the CLI confirmation; see [[Decision - Fire-and-Forget Feedback]].
- **Notification surface is asymmetric.** A Report is *not* pushed anywhere — the Fabro team discovers it out-of-band through whatever channel the Reporter shared the URL in (GitHub issue, Slack, email). A Feedback *is* pushed — the service posts a Discord message via webhook to a private team channel immediately after writing the S3 objects. See [[System - Feedback Storage & Notification]] for the push mechanics.
- **Storage layout is asymmetric.** A Report stores as a single Debug Bundle object (`bundle.tar.gz`) plus a sidecar (`metadata.json`) in a per-Report S3 prefix keyed by Report ID. A Feedback stores as `feedback.json` (structured metadata including IP, email, sysinfo) plus `feedback.txt` (the message text only) plus optional `attachments/...` under a per-Feedback S3 prefix keyed by UUIDv7. Different object layouts, different prefixes (`<YYYY>/...` for Reports; `feedback/<YYYY>/...` for Feedback), different verbs (Reports are *uploaded*, Feedbacks are *submitted* — see [[Standard - Noun Vocabulary]] Usage Rule 6 and the verb-asymmetry anti-example).

The verb asymmetry mirrors the entity asymmetry. Debug Bundles are *uploaded* (tarball bytes transferred to S3 via presigned URL, with Fargate coordinating but never carrying the bytes). Feedbacks are *submitted* (the CLI POSTs the payload directly to the service, which writes S3 objects itself and pushes Discord — see [[Standard - Interaction Patterns (CLI + Delete)]]).

## WHERE: Ecosystem

- Canonical vocabulary:
  - [[Standard - Noun Vocabulary]] — the authoritative Feedback definition (fields, relationship to Feedback Submitter, distinction from Report) lives there; this Component card is its structural expansion. Any drift between this card's field list and the Standard's field list is a defect in one of them — the Standard is authoritative. Usage Rules 6 and 7 specifically prohibit conflating Feedback with Report or Feedback Submitter with Reporter.
- Counterpart entity — asymmetric, not synonymous:
  - [[Component - Report]] — the first-class entity for the Debug Bundle flow. Feedback is the parallel first-class entity for the Feedback flow. The two entities share no fields, no ID shape, no access model, no storage layout, and no lifecycle mechanics; they share only the 30-day retention window (per [[Decision - 30-Day Retention Default]]'s extended scope). See the "Feedback is not a Report" note on that card for the counterpart framing.
- Creator role:
  - [[Agent - Feedback Submitter]] — the persona that creates a Feedback by running `fabro feedback`. The Feedback Submitter's optional email is captured as the Feedback's `email` field; the Feedback Submitter's IP is server-logged into the Feedback's `ip` field; Fabro version / platform / arch is captured from the CLI and stored on the Feedback. The Feedback is the thing the Feedback Submitter hands off; the Feedback Submitter never sees the Feedback again after submission.
- Team side of the pickup:
  - [[Agent - Triager]] — reads the Feedback first via the Discord post pushed by [[System - Feedback Storage & Notification]], and optionally retrieves the full Feedback (`feedback.json` + `feedback.txt` + any attachments) from S3 using their own AWS credentials. The Triager never interacts with the Feedback through this service; the Discord post and S3 object are the structural contracts between Feedback and Triager reading. The Triager has no delete capability on Feedback through the service — expiration is via the 30-day S3 lifecycle rule only.
- Access model:
  - [[Decision - Fire-and-Forget Feedback]] — the Feedback has no capability URL, no rendered page, and no delete action. The Feedback Submitter's involvement ends at the CLI confirmation. This Component card inherits that Decision for its post-submission semantics and explicitly does not carry a URL field, a capability-token field, or a page-addressing field of any kind. The Feedback is not addressable from outside the Fabro team's infrastructure.
  - [[Decision - Capability URLs over Auth]] — explicitly scoped to the Debug Bundle flow. Feedback does *not* inherit A9's access model; it inherits [[Decision - Fire-and-Forget Feedback]] instead. The asymmetry is load-bearing and documented on both Decisions.
- Identity-data scope:
  - [[Decision - IP Logging for Abuse Protection]] — the Feedback's `ip` field is the library's first identity-data capture. A18 is the scope commitment that binds IP logging strictly to abuse protection (no analytics, no cross-submission tracking, no marketing telemetry, no compliance audit trail). This Component card carries `ip` as an authoritative field; A18 carries the rationale and the scope ceiling.
- Retention:
  - [[Decision - 30-Day Retention Default]] — the Feedback's retention deadline is exactly 30 days from submission, immutable per-Feedback, product-owner-adjustable only as a policy. The 2026-04-23 extension of A11 from Debug-Bundle-only to both-intake-types is what makes this inheritance structural. This Component card inherits that deadline as a structural field; the *mechanism* that enforces the deadline (S3 lifecycle rule on the `feedback/` prefix) lives in [[System - Feedback Storage & Notification]].
- Relationships to other entities:
  - [[Standard - Noun Vocabulary]] — the Feedback is the submission entity; the Feedback Submitter is the role that created it; Discord channel membership is the Triager-side reading surface (but Discord channel is not a first-class noun on this service — it is an external notification target). The verb asymmetry — Debug Bundles are *uploaded*, Feedbacks are *submitted* — is vocabulary-level and must be preserved in prose.
- IA position:
  - [[Standard - Information Architecture]] — A6 captures the Feedback flow's IA shape as "no page, no URL, no listing, no routable address on the service." The Feedback occupies no position in the service's IA traversal because it has no rendered surface; the Discord post is external. The minimal-IA identity of the Debug Bundle flow has a parallel minimal-IA on the Feedback side: even more minimal, in fact, because there is no Report-Metadata-Page-equivalent.
- Scope commitments:
  - [[Product Thesis - Pickup Point, Not Triage Surface]] — the Feedback is the pickup receipt for the voice intake. Its fields are calibrated to "capture enough of what the Feedback Submitter said and who they are (abuse-protection scope) for the Fabro team to read the message in Discord and optionally pull more from S3" and nothing more; Feedback-level fields that serve a forum workflow (read state, reply thread, submitter dashboard, topic tags for classification) are out of scope.
  - [[Principle - Narrow Forever]] — adding fields to the Feedback is a scope question, not an implementation question. The field list in [[Standard - Noun Vocabulary]] is the complete field list; extending it requires updating that Standard (and its backing source) first. The Feedback is also the entity whose existence the 2026-04-23 ceiling-at-two-intake-types locks; a third entity corresponding to a third intake type would require an identity-change conversation.
  - [[Principle - Reject Like bun.report Drift]] — `bun.report`-shaped Feedback enrichment (threading, topic classification, submitter dashboards, "my feedback" views, feedback analytics) is named drift; this Component card inherits the rejection.
- Mechanism and UX:
  - [[System - Feedback Storage & Notification]] — the mechanism that persists the Feedback to S3 (`feedback.json` + `feedback.txt` + optional `attachments/...` under `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/`), pushes it to the team's Discord channel via webhook, and self-reports if the webhook call fails. Policy lives in [[Decision - Fire-and-Forget Feedback]], [[Decision - IP Logging for Abuse Protection]], and [[Decision - 30-Day Retention Default]]; mechanism lives there.
  - [[Standard - Interaction Patterns (CLI + Delete)]] — the CLI UX that creates the Feedback (`fabro feedback` with positional text / files, `-e, --email` flag, stdin acceptance, confirmation line) and the explicit no-delete commitment on the Feedback flow. A7's "No Delete on the Feedback Flow" subsection is the interaction-layer expression of the fire-and-forget commitment this Component card inherits.
- Paired service topology:
  - [[System - Service Topology]] — the operational pieces the Feedback's creation traverses: Fargate task accepts `POST /v1/feedback`, writes the Feedback's S3 objects using its IAM role, posts to Discord via the `FEEDBACK_DISCORD_WEBHOOK_URL` secret. Discord is the first non-AWS third-party egress in the topology, added 2026-04-23.

## WHY: Rationale

The Feedback has a card of its own because it is a first-class entity distinct from the Report in every structural way that matters — ID shape, access model, notification surface, storage layout, verb — and collapsing the two entities into one card would force a Frankenstein field list that describes both Report and Feedback, which is exactly the atomicity violation that [[Standard - Noun Vocabulary]] Usage Rules 6 and 7 exist to prevent. Giving the Feedback a dedicated Component card surfaces its field list and lifecycle in one place so downstream implementation has a single structural reference; keeping the Component card thin — authoritative vocabulary in [[Standard - Noun Vocabulary]], policy in the Decisions, mechanism in [[System - Feedback Storage & Notification]] — keeps the Feedback card from becoming a catch-all spec that silently accumulates scope.

The load-bearing coupling is *the Feedback is the envelope, not the message*. `feedback.txt` carries the message text; `feedback.json` carries the envelope metadata (UUIDv7, IP, email, Fabro version / platform / arch, timestamp, retention deadline, file attachments manifest); optional `attachments/` objects carry the files. The Feedback (the Component) names the envelope and the submission event; the contents of `feedback.txt` and the attachments are the message the Feedback Submitter sent. The distinction parallels [[Component - Report]]'s *the Report is not the Debug Bundle* — a Report is a handle on an opaque bundle; a Feedback is an envelope around a message. Both Components name the first-class entity; both defer the payload's internal semantics (bundle contents, message contents) to the Feedback Submitter / Reporter and to out-of-band Fabro team tooling.

## HOW: Specification

### Authoritative Fields

Each field below appears in [[Standard - Noun Vocabulary]]'s Feedback entry and is reproduced here with its structural role. The Standard is authoritative for naming and short definitions; this card names the structural role each field plays.

- **ID (UUIDv7)** — the Feedback's internal identifier. Server-generated at the moment the `POST /v1/feedback` request is received. Time-ordered by UUIDv7's design (the timestamp prefix orders submissions chronologically when Triagers list the `feedback/` S3 prefix by key). Used as the `<uuidv7>` segment of the S3 key scheme (see [[System - Feedback Storage & Notification]]). **Does not need to be cryptographically unguessable**, unlike a Report's 128-bit-entropy ID — because the Feedback is not capability-URL-addressed, there is no "guess the ID and gain access" attack surface. UUIDv7 is a structural fit for a fire-and-forget entity with no guessability requirement.
- **Message text (optional)** — the free-form text content of the submission. Stored as `feedback.txt` in S3, distinct from the structured metadata in `feedback.json`. Absent if the Feedback Submitter submitted only file attachments with no text. No size cap is specified at the Component layer; implementation-level caps are governed by [[System - Feedback Storage & Notification]] and Discord's file/message size constraints.
- **File attachments manifest (optional)** — a structured list of the file attachments the Feedback Submitter included with the submission. Stored inside `feedback.json` as a manifest (filename, size, content-type, storage-key); the file bytes themselves are stored as separate S3 objects under `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/attachments/...`. Absent if the Feedback Submitter submitted only text with no attachments.
- **Email (optional)** — the attribution email passed via the `-e, --email` flag at CLI time, if the Feedback Submitter chose to attach one. Treated as an **opaque string**: not validated for format at the service layer, not used as an account token, not used to authorize any subsequent action, not used to group submissions into a "my feedback" view, not used as a service-initiated notification target. Rendered as the header (`## <email>`) of the Discord post if present; a neutral placeholder is used if absent. Per [[Standard - Noun Vocabulary]], `email` is part of the Feedback Submitter's identity model — not an account concept.
- **Client IP (server-captured)** — the client IP observed by the Fargate task at the moment of the `POST /v1/feedback` request. Written into `feedback.json` alongside other metadata. Retained for the standard 30 days (no separate lifecycle). **Scope of use is strictly abuse protection** per [[Decision - IP Logging for Abuse Protection]]: detecting submission floods, correlating repeated abuse from one IP. Never used for analytics, cross-submission tracking, marketing telemetry, compliance audit trail, or geolocation surfacing. This is the library's first capture of identity-adjacent data; A18 is the scope guardrail.
- **Fabro version / platform / arch** — captured by the CLI as part of the request payload. Stored in `feedback.json`. Appears as the sysinfo one-liner in the Discord post (e.g., "Fabro v<version> <platform> <arch>" — see [[System - Feedback Storage & Notification]] for the exact payload shape).
- **Timestamp** — the submission moment, measured by the service when `POST /v1/feedback` is received. Embedded in the UUIDv7 (which is time-ordered) and also stored explicitly in `feedback.json`. Used to compute the retention deadline.
- **Retention deadline** — submission timestamp plus 30 days, per [[Decision - 30-Day Retention Default]]. Feedback-Submitter-immutable; product-owner-adjustable only as a policy, not per-Feedback. At the deadline, the Feedback's S3 objects (`feedback.json`, `feedback.txt`, any attachments) are deleted by the S3 lifecycle rule that applies to the `feedback/` prefix. The Discord post itself is not deleted by this service — Discord's own retention governs it.

### Storage Layout (Load-Bearing)

Each Feedback occupies one S3 prefix: `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/`. Inside that prefix:

- `feedback.json` — the structured envelope metadata (all fields above except Message text).
- `feedback.txt` — the message text, if any. Stored as a separate object from `feedback.json` so a Triager reading the Discord post can follow the S3 link and read the message directly without parsing JSON, and so the text is independently retrievable without the full metadata envelope.
- `attachments/<original-filename>` — one object per attached file, if any. Filenames preserved as the Feedback Submitter named them (with implementation-level sanitization where security requires); content is stored as uploaded.

The `feedback/` prefix is distinct from the Debug Bundle prefix (`<YYYY>/<MM>/<DD>/<id>/` under the bucket root, with no `feedback/` segment) per [[System - Feedback Storage & Notification]]. The two prefixes share a bucket but are otherwise independent. Feedback objects are **never** written to the Debug Bundle prefix and vice versa.

### Lifecycle

A Feedback has exactly three lifecycle events, and no other states.

1. **Created at successful submission.** `fabro feedback` POSTs the payload to `/v1/feedback` on the Fargate service. The service mints a UUIDv7, writes `feedback.json` + `feedback.txt` + any attachments to S3 under `feedback/<YYYY>/<MM>/<DD>/<uuidv7>/`, posts the Discord notification, logs the submission to server logs (structured, per [[System - Feedback Storage & Notification]]), and returns a confirmation to the CLI. Creation is atomic with the S3 write and the Discord post; if either fails, the failure-self-reporting path in A17 applies, and the Feedback either completes fully or self-reports its partial state to the team.
2. **Read (optionally) by a Triager.** Triagers discover Feedback through the Discord post pushed by [[System - Feedback Storage & Notification]]; they may optionally retrieve the full Feedback from S3 using their own AWS credentials. Reads do not modify the Feedback; there is no "read" state. No counting of reads, no last-read timestamp, no viewed-by flag.
3. **Auto-deletes at retention deadline.** At the 30-day boundary, the S3 lifecycle rule deletes all objects under the Feedback's prefix. The Feedback is no longer retrievable from the service's storage. The Discord post itself is not deleted by this service — Discord's own retention governs it, and a Triager who needs a record of the Feedback beyond 30 days can extract it from Discord or copy the S3 objects before expiration. (The same principle applies to Debug Bundles per [[Component - Report]] lifecycle step 4.)

No modification after creation is possible. There is no edit operation. There is no delete operation for the Feedback Submitter — [[Decision - Fire-and-Forget Feedback]] is the upstream commitment that rules out a delete capability, [[Standard - Interaction Patterns (CLI + Delete)]] "No Delete on the Feedback Flow" is the interaction-layer expression of it, and this Component card inherits the no-delete posture as a structural property.

### Key Couplings (Load-Bearing)

- **A Feedback is the envelope; `feedback.txt` / attachments are the message.** This is the most important coupling the card expresses. The Feedback names the submission event and the storage identity; the contents of `feedback.txt` and the attached files are the message the Feedback Submitter sent. See [[Standard - Noun Vocabulary]] for the entity distinction; see [[Product Thesis - Pickup Point, Not Triage Surface]] for why the service never collapses envelope and message into a single "Feedback content" concept.
- **A Feedback has no capability URL.** Not an unguessable one, not a guessable one, not a time-limited one, not one returned to the Feedback Submitter. The Feedback is not externally addressable. See [[Decision - Fire-and-Forget Feedback]]. The UUIDv7 is an internal identifier used for S3 key generation and server-log correlation; it is never rendered into a user-shareable URL.
- **A Feedback is pushed to Discord, and Discord is the primary team-reading surface.** The S3 objects are the authoritative persistence; the Discord post is the fast-path surface a Triager reads first (per [[Agent - Triager]]'s Feedback workflow, primary step). If the Discord post carries everything the Triager needs, S3 is never consulted. The push-target nature of Discord is load-bearing; the service is not responsible for Discord's availability, search, or retention.
- **A Feedback's retention deadline is 30 days from creation, not adjustable.** See [[Decision - 30-Day Retention Default]]. The deadline is a structural field, not a configurable one; a Feedback Submitter cannot extend retention, cannot shorten it, cannot opt out of it. Neither can a Triager, through this service — Triagers who need a Feedback beyond 30 days copy the S3 objects into their own tooling before expiration.

### Anti-Examples (What a Feedback Is Not)

- **Wrong:** Treating the Feedback as capability-URL-addressed. Adding a URL field to the Feedback, returning a URL from `fabro feedback` on success, or rendering a Feedback Submitter-facing page at a URL derived from the UUIDv7. This re-introduces a post-submission submitter-facing surface the Feedback flow is designed not to have and violates [[Decision - Fire-and-Forget Feedback]]. The correct answer to "the Feedback Submitter wants to revisit their submission" is: they cannot, through this service; the service is not the memory of their submission.
- **Wrong:** Treating the UUIDv7 as a secret. UUIDv7 is time-ordered and guessable in the sense that an attacker with rough timing could narrow the search space substantially — which is *fine* because the UUIDv7 is not used as a capability token. No feature should depend on UUIDv7 secrecy; if one did, the Feedback's ID shape would be wrong and the correct fix is to widen the scope of [[Decision - Fire-and-Forget Feedback]] or of [[Decision - Capability URLs over Auth]] (neither of which apply to Feedback today).
- **Wrong:** Adding a mutable state field (read state, reply thread, topic tag, investigation status, team assignee). The Feedback has no mutable state after creation. Any proposed mutable field is a scope expansion that must go through [[Principle - Narrow Forever]] and the product owner.
- **Wrong:** Adding an ACL, owner ID, or "shared with" list on the Feedback. The access model is fire-and-forget; introducing any identity-bound access concept on the Feedback side violates [[Decision - Fire-and-Forget Feedback]] and re-introduces the account-shaped surface the Feedback flow refuses.
- **Wrong:** Using the optional email as an account key or a cross-submission join field. The email is opaque attribution for Discord post shaping; it is not validated, not indexed, not used to group or classify submissions on the service side. Any feature that treats the email as a stable user identifier has widened it beyond its authorized scope and contradicts [[Standard - Noun Vocabulary]] Usage Rule 7.
- **Wrong:** Using the server-logged IP for anything except abuse protection. Surfacing IP in analytics, cross-referencing IPs across submissions for "same user" detection, using IP to geolocate submissions, using IP as part of a compliance audit trail. Each of these is a scope violation against [[Decision - IP Logging for Abuse Protection]] and must be rejected at the Component layer, not deferred to A18.
- **Wrong:** Adding a content hash or canonical-feedback pointer. Feedback dedup is not a question anyone asks — Feedback is voice, not reproducibility data, and two identical messages from two Feedback Submitters (or from one Feedback Submitter at different moments) are two separate pieces of voice. The analogous rejection for Debug Bundles lives in [[Decision - No Content Dedup]]; the Feedback side inherits the same posture without needing a separate Decision card (no one has proposed Feedback dedup; the structural reason is the same — each submission is its own thing).
- **Wrong:** Calling a Feedback a "Report" — e.g., "the Feedback Submitter's Report was posted to Discord." Report is the upload event / public identity for a Debug Bundle upload; Feedback is the submission entity for the Feedback flow. See [[Standard - Noun Vocabulary]] Usage Rule 6.

### Test

Before describing a Feedback in a downstream card or CLI string, check two things. First, does every field named appear in [[Standard - Noun Vocabulary]]'s Feedback entry? If not, that is synonym drift or field invention and must be reconciled with the Standard first. Second, does the description assume any Feedback capability beyond "create via `fabro feedback`, get pushed to Discord, optionally read from S3 by Triagers with own AWS credentials, auto-expire at 30 days"? If yes, that is a scope expansion that must clear [[Principle - Narrow Forever]] and the relevant Decision (A18 for identity-data scope, A19 for post-submission access); it is not a Component-level implementation choice.
